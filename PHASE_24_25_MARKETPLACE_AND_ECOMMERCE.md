# Phase 24 (Marketplace Foundation) + Phase 25 (E-Commerce) — Build Log

**Status: IMPLEMENTED, TESTED, ships fully disabled.** Built together in one pass, per the reasoning in `PHASE_24_MARKETPLACE_FOUNDATION_ARCHITECTURE.md §9`: a foundation with zero working implementer is unprovable, and real evidence (6amMart) shows all four Marketplace verticals share ONE schema, unlike the genuinely divergent Family A/B domains — so building the foundation and its first prover together is the correctly-sized increment, not premature scope combination.

See `PHASE_24_MARKETPLACE_FOUNDATION_ARCHITECTURE.md` for the full evidence trail and design decisions (Vendor→Provider+Store correction, shared `marketplace_orders` table, self-referential categories, relational `product_variants`, stock-lock concurrency model, dispatch reuse). This document is the build log: what was actually implemented, and the honest status of Phases 26-28.

## What was built

**Schema (12 new migrations, all additive):** `stores`, `marketplace_categories` (self-referential), `products`, `product_variants`, `add_ons`, `cart_items`, `marketplace_orders`, `marketplace_order_items`, `marketplace_order_status_history`, `marketplace_order_sequences`, plus nullable `marketplace_order_id` FKs on `commissions`/`payments`/`reviews` (same one-column-per-purpose precedent every prior vertical uses). `dispatch_attempts` needed no migration — its polymorphic `dispatchable_type`/`dispatchable_id` columns (Phase 22.4) already accept `MarketplaceOrder` directly.

**Models:** `Store`, `MarketplaceCategory`, `Product`, `ProductVariant`, `AddOn`, `CartItem`, `MarketplaceOrder` (the fifth `Orderable` implementer — the first whose `moduleCode()` is dynamic, reading the order's own `module` column rather than a fixed constant, since it genuinely serves four verticals), `MarketplaceOrderItem`, `MarketplaceOrderStatusHistory`. `Provider::stores()` added (multi-location reuse, mirroring `properties()`).

**Services/Actions:** `CartService` (add/merge/update/remove, browse-time only — not the concurrency boundary), `CreateMarketplaceOrderAction` (checkout: module gate, minimum-order/delivery-fee/tax calculation, `lockForUpdate()` stock decrement with an availability re-check for products/variants deactivated after being cart-added, cart clearing, wallet payment), `AdvanceMarketplaceOrderAction` (store-side pending→accepted→preparing→ready, one action with a transition map rather than three near-identical classes — a deliberate, documented simplification from Property Rental's one-class-per-transition precedent since these three share identical side effects), `CompleteMarketplaceOrderAction` (ready→completed, covers both `delivery` — OTP-gated, rider-completed — and `pickup` — store-completed, no OTP — in one action), `AcceptMarketplaceDeliveryOfferAction` (rider accepts a real dispatch offer), `AdminCancelMarketplaceOrderAction` (cancel + stock release, mirroring `PropertyAvailabilityService::releaseDates()`'s own transactional placement). `CommissionService::applyForMarketplaceOrder()` (fifth caller of the shared `applyForFieldWorkerOrder()` helper, earner = `$order->store?->provider`). `CancellationService::calculateFeeForMarketplaceOrder()`/`refundIfPaidForMarketplaceOrder()` (elapsed-since-creation generic formula, matching Parcel/Taxi's precedent — no vertical-specific window invented). `DispatchService::findMarketplaceDeliveryRiderCandidates()` (third real consumer of the shared `rankedFieldWorkerCandidates()` core; the first whose capability type is chosen at runtime from the order's own `module`). `MarketplaceDispatchJob` (structural mirror of `ParcelDispatchJob`). `OrderCodeService::generateForMarketplaceOrder()` (`-MKT-` segment, one shared sequence across all four verticals — the shared-order-table decision applied to code generation too).

**Registry additions:** `App\Support\Modules::FOOD`/`::GROCERY`/`::PHARMACY`/`::COMMERCE` constants (the slugs already existed in `Modules::ALL`; this closes the same string-literal gap every prior vertical's own constant already avoided). `App\Support\WorkerTypes::commerce_delivery_rider`/`::pharmacy_delivery_rider` (symmetric completion of the existing `food_delivery_rider`/`grocery_delivery_rider` pair, Phase B0.1).

**Admin (5 new screens, `/admin/stores`, `/admin/marketplace-categories`, `/admin/products`, `/admin/add-ons`, `/admin/marketplace-orders`):** all row-scoped via `AuthorizationService::scopeQuery()` — `Product`/`AddOn` scope through their owning `store` relation using this codebase's existing dotted-relation-path convention (`'city_id' => 'store.franchise.city_id'`), the same mechanism already proven for direct franchise/zone columns, now proven for a one-hop-removed relation too. New permissions: `stores.manage`, `marketplace_categories.manage`, `products.manage` (covers variants/add-ons as sub-resources, no separate permission — mirrors how Property Rental's variants-equivalent concepts never got their own permission either), `marketplace_orders.view`/`.cancel`.

**API:** public browse (`GET /api/stores`, `/api/stores/{id}`, `/api/stores/{id}/products`, `/api/products/{id}` — unauthenticated, same justification `PropertyController`'s own docblock gives: real evidence this is a genuine self-service browse domain), authenticated cart (`GET/POST /api/cart`, `PATCH`/`DELETE /api/cart/{id}`), checkout (`POST /api/marketplace-orders`), customer order history (`GET /api/marketplace-orders/mine`, `/{id}`), delivery rider job flow (`GET /api/worker/marketplace-orders`, `POST .../accept`, `POST .../deliver`).

## Real defects found and fixed during this phase's own hardening pass

1. **Model fillable gaps** (`Commission`/`Payment`/`Review` were each missing `marketplace_order_id` in their `$fillable` arrays despite the migrations adding the column) — caught by the lifecycle test suite itself (a commission/payment silently failed to persist its FK, then the idempotency test's second `applyForMarketplaceOrder()` call didn't find the "already exists" row and attempted a real double wallet credit, caught by the wallet ledger's own unique-ref constraint). Fixed before commit, not after.
2. **Checkout didn't re-validate `is_active`/`is_approved`** on products/variants at the authoritative checkout boundary — a product could be browsed and cart-added while live, then deactivated by its store before checkout actually ran, and the stale cart line would silently still be honored. Fixed inside the same `lockForUpdate()` step that already handles stock, same "browse-time filter is not the safety check" discipline as stock itself.
3. **Add-ons weren't verified to belong to the same store as the product being cart-added** — a customer could reference a cheaper add-on's id from an unrelated store. Fixed with a real store-match check in `CartController::store()`.

All three closed with regression tests proven to fail pre-fix, matching this mission's own established verification discipline throughout.

## Phase 26-28 (Food / Grocery / Pharmacy) — real disposition, not a placeholder

Per architecture doc §9 and `MarketplaceMultiVerticalReuseTest` (5 tests, all passing): **no new table, model, action, admin screen, or API endpoint is needed for any of the three.** A `Store`/`Product`/`MarketplaceOrder` row with `module = 'food'`/`'grocery'`/`'pharmacy'` runs through the byte-identical code path `'commerce'` (Ecommerce, Phase 25) already exercises — proven directly, not asserted: a full food order lifecycle (checkout→accept→preparing→ready→completed, real commission), a full grocery order (real stock decrement), a pharmacy store with `prescription_required = true` (the one real evidenced Pharmacy-specific control, with honestly zero invented verification workflow around it — per the mission's own "no invented business rules" discipline), each vertical's own independent module-activation toggle (`food` active while `grocery` stays correctly blocked), and `DispatchService` correctly routing delivery offers to the right `WorkerTypes` capability per order module (a `food_delivery_rider` matched, a `grocery_delivery_rider`/`pharmacy_delivery_rider`/`commerce_delivery_rider` correctly excluded from the same search).

This means Phases 26-28 are **functionally complete the moment Phase 24/25 shipped** — the only remaining work per-vertical is business-side catalog population (real stores/products/categories for that vertical) and the module-activation decision to actually turn each one on for a real franchise, neither of which is engineering work this mission performs (inventing sample store/product data would be fabricating business content, not building infrastructure).

**BUSINESS DECISION REQUIRED (Pharmacy only, named honestly, not invented around):** What actually happens between "an order is flagged `prescription_required`" and "the order is accepted" — upload-and-review, pharmacist sign-off, or something else — is a real regulatory/operational question this phase does not invent an answer to. The flag and its schema are real and ready; the workflow behind it is not built.
