## 2. Correction to Phase 22.8: `Vendor` is two real concepts, not one

Phase 22.8 decided a single new `vendors` table (one row per physical location, no Branch layer), based solely on Glover's flatter model. Direct read of 6amMart's real `Vendor.php`/`Store.php` shows something Glover's evidence didn't have: **`Vendor extends Authenticatable` (the login/account) `hasMany Store` (`Store belongsTo Vendor`, `Item belongsTo Store`, `Order belongsTo Store`)** — a genuine two-tier real design, not a Branch layer invented for hierarchy's own sake. `Store` carries every location-specific column (`zone_id`, `module_id`, delivery/tax/commission settings, `prescription_order`); `Vendor` is purely the account.

This codebase already has the exact account-tier entity 6amMart's `Vendor` represents: **`Provider`** (`belongsTo User`, KYC status, already the reused owner-identity for Property Rental's `properties.provider_id`). Per Phase 22.8 §2c's own reasoning — reuse an identity when the new entity needs none of its columns and adds none of its own — the evidence-correct shape is:

- **No new `vendors` table.** `Provider` is reused as the account/owner tier, exactly like Property Rental already reuses it for `properties.provider_id`. Zero new columns needed on `Provider` — a store owner needs nothing Provider doesn't already have.
- **New `stores` table** — the real per-location, catalog-owning, franchise/zone-scoped entity 6amMart's `Store` (and Glover's flatter single-tier `Vendor`) both actually are. `stores.provider_id` is the account link. This also directly answers Phase 22.8 §6's own "genuinely undecided" multi-location/multi-staff question the old design left open: **a `Provider` can own multiple `Store` rows** (one real account, several physical locations/zones) — the exact shape 6amMart's real `Vendor hasMany Store` evidence shows, arrived at through this codebase's own reuse convention rather than inventing a parallel one.

This is a genuine correction driven by better evidence, made before any marketplace code existed (Phase 22.8 shipped no `vendors` table — a design doc only), so nothing is broken or migrated away from.

## 3. Catalog: `Store` → `MarketplaceCategory` → `Product` → `ProductVariant`

- **`stores`** — `provider_id`, `franchise_id`, `zone_id`, `module` (string, matching `App\Support\Modules::ALL` keys — `food`/`grocery`/`pharmacy`/`commerce` — same established convention `service_categories.module` already uses, confirmed by reading that migration directly; **not** a FK to the `modules` table, matching that same precedent), name/slug/description/logo/cover_image, address/lat/lng, `is_open` (real-time toggle), `is_active` (admin toggle), `prescription_required` (real 6amMart evidence, `stores.prescription_order` — the one genuinely evidenced Pharmacy-specific control), `tax_percent`, `minimum_order_amount`, `delivery_fee_flat`, `free_delivery_above_amount` (nullable — no free-delivery threshold by default, matching "no invented value" discipline). **Deliberately NOT built**, real evidence exists for it but it's not required to prove a working checkout: `store_schedules` (day-by-day opening hours — `is_open` is a real, simpler, evidenced mechanism on its own; 6amMart's `StoreSchedule` table is a genuine enhancement, not a prerequisite), a store-level commission-rate override (6amMart's `stores.comission` — the shared `applyForFieldWorkerOrder()` helper only reads `franchise->platform_fee_percent` today; widening it for an unproven per-store override would be exactly the premature-generalization trap this mission warns against), a subscription-package-per-store revenue model (`package_id` — a genuine commercial model 1CallFix has never used anywhere).
- **`marketplace_categories`** — self-referential (`parent_id` nullable FK to itself), `module`-scoped, `name`/`slug`/`image`/`position`/`is_active`. Real evidence favors ONE self-referential table over Glover's/this codebase's own separate-Category-+-Subcategory convention (`ServiceCategory`/`ServiceSubcategory`, `PropertyType`): 6amMart's real `categories` table is genuinely self-referential (`parent_id`), not two tables. Deliberately not forced through `ServiceCategory` (a Service-specific taxonomy already, per Property Rental's own precedent of not reusing it for `PropertyType`) or given its own two-table Subcategory split (no evidence requires it once a real self-referential option exists).
- **`products`** — `store_id`, `marketplace_category_id`, `name`/`slug`/`description`/`images` (JSON array), base `price`, `tax_percent`, `discount_percent` (nullable), `stock` (integer — real 6amMart evidence: even their own schema keeps base stock as one integer column, not a separate Inventory table, when a product has no variants), `is_approved` (real evidence — a genuine multi-vendor moderation gate: `is_approved=false` products never surface in the public catalog until an admin reviews them, defaulting to `true` since a single-operator-approved franchise structure doesn't need pre-moderation by default, but the column and admin action are real, not decorative), `is_active`.
- **`product_variants`** — a real, evidence-motivated improvement over 6amMart's own flat JSON `variations`/`choice_options` columns: a genuine relational table (`product_id`, `name` e.g. "Large / Red", `sku` nullable, `price_override` nullable — falls back to the product's base price when null, `stock` integer, `is_active`). The roadmap's own "Variants → Inventory" being two distinct steps is real evidence FOR a relational table over a JSON blob — a JSON column can't carry its own per-variant stock count safely under concurrent decrement (see §5). Cart/order lines reference `product_id` + nullable `product_variant_id`, matching 6amMart's real cart/order-line shape.
- **`add_ons`** — `store_id`, `name`, `price`, `is_active`. Direct match to 6amMart's real `add_ons` table (simple, no addon-category sub-table — no evidence that extra tier is required to prove the architecture).

## 4. Cart → Checkout → `MarketplaceOrder` — one shared table across all four verticals, a deliberate divergence from Phase 22.2's own precedent

Phase 22.2 (Order Engine) decided each Family-A vertical gets its own dedicated order table (`Booking`/`ParcelOrder`/`TaxiRide`), based on real evidence that Glover keeps Taxi's own order table separate from its generic `Order`. That was the right call **for that evidence**. Here, the evidence points the other way, and this document follows it rather than mechanically repeating the prior pattern: **6amMart's own real `orders` table is genuinely ONE shared table across Food/Grocery/Pharmacy/Ecommerce**, differentiated by a `module_id` column on the row itself — not four separate order tables. This is real, direct, and the opposite of Glover's Taxi-vs-Order split, which is exactly why Family A's per-vertical-table precedent doesn't mechanically transfer here: the two reference products made two different real design choices for structurally different situations (Taxi has a materially different lifecycle from generic delivery orders; Food/Grocery/Pharmacy/Ecommerce genuinely don't from each other).

- **`cart_items`** — matches 6amMart's real flat-row shape exactly (no separate Cart "header" row anywhere in their evidence either): `user_id`, `store_id`, `product_id`, `product_variant_id` (nullable), `quantity`, `add_on_ids` (JSON), `unit_price_snapshot` (priced at add-time, matching real evidence rather than re-pricing live on every cart view). A user can hold simultaneous carts across different stores (`store_id` scopes rows, no cross-store cart merge — matches real evidence directly).
- **`marketplace_orders`** — `code` (own `-MKT-` sequence, same `OrderCodeService` per-franchise-per-day atomic-increment pattern every prior vertical uses), `franchise_id`, `zone_id`, `customer_id`, `store_id`, `module` (redundant with `stores.module` by design — real 6amMart evidence keeps `module_id` on BOTH `stores` and `orders`, useful for direct reporting without a join, same reasoning `property_reservations` duplicates `zone_id` from `properties`), `order_type` (`delivery`/`pickup` — real evidence), `delivery_address_id` (nullable FK to the existing `addresses` table, reusing Parcel's own precedent, not a new address table), `subtotal`/`delivery_fee`/`tax_amount`/`discount_amount`/`total_amount`, `status` (own conceptual FSM, not 6amMart's one-timestamp-per-status sprawl — see §4a), `payment_status`/`payment_method` (matching every other vertical), `cancellation_reason_id`/`cancellation_note`/`cancellation_fee` (reusing `CancellationReason`), `coupon_code`/`coupon_discount_amount` (schema present, matching real evidence — **not wired to live `Coupon` redemption**, since `KNOWN_RISKS_AND_DECISIONS.md` item 12's stacking rules are still genuinely undecided; wiring it now would be exactly the kind of invented-policy risk this mission avoids elsewhere), `special_instructions`, `confirmed_at`/`ready_at`/`completed_at` (a FEW key lifecycle timestamps, not one-per-status like 6amMart — matching Property Rental's own precedent of a compact set of timestamps plus a full status-history table for the granular audit trail).
- **`marketplace_order_items`** — `marketplace_order_id`, `product_id` (nullable, `nullOnDelete` — a sold order line must survive its catalog row being deleted later), `product_variant_id` (nullable), `product_name_snapshot`/`variant_name_snapshot` (real evidence: 6amMart's own `item_details`/`variant` columns are exactly this kind of point-in-time snapshot, preserving order-history accuracy independent of later catalog edits), `quantity`, `unit_price`, `add_ons_snapshot` (JSON), `add_ons_total`, `line_total`.
- **`marketplace_order_status_history`** — mirrors `property_reservation_status_history` exactly.
- **`marketplace_order_sequences`** — mirrors `property_reservation_sequences` exactly, for `OrderCodeService`'s atomic per-franchise-per-day increment.

### 4a. Status FSM

`pending → accepted → preparing → ready → completed`, `cancelled` from any non-terminal state. Deliberately unified across `order_type` (`delivery` and `pickup`) rather than inventing two divergent vocabularies: `ready` means "ready for rider pickup" for delivery orders and "ready for customer pickup" for pickup orders; `completed` means "delivered" or "collected" respectively. Each name traces directly to real 6amMart status concepts (`confirmed`/`processing`/`handover`&`picked_up`/`delivered`) collapsed into this codebase's own proven compact-FSM shape (matching Booking/ParcelOrder/TaxiRide/PropertyReservation's own precedent) rather than reproducing 6amMart's full one-column-per-status-timestamp sprawl, for which no evidence says THIS codebase needs it.

## 5. Concurrency safety: stock decrement is a real backstop, structurally simpler than Property Rental's date-locking

Property Rental needed a two-part design (`lockForUpdate()` on existing rows + a UNIQUE constraint backstop) because a date row might not exist yet, so two concurrent transactions could both attempt to INSERT the same not-yet-existing slot — no row to lock. Stock decrement is structurally different: the `products`/`product_variants` row **already exists** the moment checkout runs (it was created at catalog-management time, not reservation time), so `lockForUpdate()` on the existing row inside the checkout transaction is itself the complete guarantee — a second concurrent transaction blocks until the first commits or rolls back, then re-reads the now-current quantity. No UNIQUE-constraint backstop is needed here because there's no "two inserts racing to create the same row" case to backstop. This is a real, evidence-based difference in the two domains' concurrency shape, not an inconsistency between them.

## 6. Fulfillment: reuse `FieldWorker` dispatch — evidence already existed in this codebase before this phase

`App\Support\WorkerTypes::ALL` already registers `food_delivery_rider`/`grocery_delivery_rider` (Phase B0.1) — real, pre-existing evidence this exact reuse was anticipated before Marketplace itself existed. This phase adds the two missing, symmetric entries (`commerce_delivery_rider`, `pharmacy_delivery_rider`) rather than inventing a new dispatch mechanism. `dispatch_attempts`' order-side polymorphism (`dispatchable_type`/`dispatchable_id`, added generically in Phase 22.4/Parcel) accepts `MarketplaceOrder` directly — zero new migration needed for dispatch itself. Only `delivery`-type orders in `ready` status become dispatch-eligible; `pickup`-type orders never dispatch (the customer collects in person, matching 6amMart's real `order_type` distinction).

## 7. Payment / Commission / Settlement — reused unchanged

- **Payment**: `payments.marketplace_order_id` nullable FK, same one-column-per-purpose precedent `parcel_order_id`/`taxi_ride_id`/`property_reservation_id` already established. No new payment engine.
- **Commission**: `CommissionService::applyForFieldWorkerOrder()` gets its FIFTH real caller (`applyForMarketplaceOrder()`), earner = `$order->store?->provider` (the store's owning Provider) — the exact same `FieldWorker|Provider` type hint Phase 22.7 already widened, unchanged again. `commissions.marketplace_order_id` nullable FK, same pattern.
- **Reviews**: `reviews.marketplace_order_id` nullable FK, same pattern. Per-product reviews (6amMart's real `ProductReview`) are real evidence but not built this phase — order-level review is sufficient to prove the architecture; a product-review sub-system is a genuine, documented future enhancement, not required scope.

## 8. Module registration — already existed, just needed constants

`App\Support\Modules::ALL` already lists `food`/`grocery`/`pharmacy`/`commerce` (added in an earlier phase, `is_implemented` still `false` for all four — confirmed by reading the file directly). This phase adds real PHP constants (`Modules::FOOD`/`::GROCERY`/`::PHARMACY`/`::COMMERCE`) matching the existing `SERVICE`/`PARCEL`/`TAXI`/`CAR_RENTAL` pattern — no new slugs invented, just closing a real gap (string literals used directly instead of named constants) the same way every prior vertical's own constant already avoids.

## 9. What Phase 24 builds vs. what Phase 25 (Ecommerce) proves

Per the user's own roadmap: Phase 24 is the shared foundation, Phase 25 is the first real implementer that proves it end-to-end. Given real evidence (6amMart) that all four verticals share ONE real schema (unlike Family A/B's genuinely divergent domains), building the foundation and Ecommerce together in one pass is the correct-sized increment — a foundation with zero working implementer is unprovable, exactly the same reasoning that made Property Rental "the reservation architecture's first real implementation" rather than a separate abstract-first pass. Food/Grocery/Pharmacy (Phases 26-28) then genuinely are thin reuse passes: new `Store`/`Product`/`MarketplaceCategory` rows scoped to their own `module` value, their own module-activation toggle, and (Pharmacy only) the one real evidenced control (`prescription_required`) — no new tables.
