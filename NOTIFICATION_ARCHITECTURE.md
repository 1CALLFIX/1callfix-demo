# Notification Architecture

## What already existed (confirmed, not assumed — `AUTH_FORENSIC_DISCOVERY.md`)

A real, clean, already-in-use abstraction: `SmsAdapter`/`PushAdapter` contracts, `SmsChannel`/`PushChannel` (Laravel notification channels), bound by default to `LogSmsAdapter`/`LogPushAdapter` (`AppServiceProvider::register()`). `ChannelResolver` turns an admin-configurable `notifications.channels` Setting into actual channel classes, scope-cascaded the same way every other Setting in this app is. This is genuinely good, swap-in-ready infrastructure — the gap was never the abstraction, it was that no real external provider (Firebase/FCM, Twilio/MSG91) is plugged in behind it, confirmed authoritatively via `config/services.php` having neither key.

**This session did not build a second notification system.** `OtpNotification` extends Laravel's `Notification` exactly like `BookingStatusNotification`/`PaymentStatusNotification` already do, and `OtpService` calls the exact same `SmsAdapter` binding everything else uses.

## Why OTP delivery bypasses `ChannelResolver` specifically (a real, deliberate decision this session)

`ChannelResolver::resolve()` defaults to `mail` when no `notifications.channels` Setting exists. That default is correct for booking-status/marketing copy (an email fallback makes sense there) and wrong for OTP (a phone-only login has no email address at all). `OtpService` therefore always uses `sms` as the channel, independent of the generic `notifications.channels` Setting — OTP delivery channel selection is its own concern, not the one `ChannelResolver` was built to solve. This is recorded in `OTP_DELIVERY_MATRIX.md`'s "DELIVERY CHANNEL" column per purpose, which is the intentionally more granular replacement for a single global setting in this specific case.

## A real framework subtlety found and worked around this session

Laravel's ad-hoc `Notification::route('sms', $phone)->notify(...)` was the initially-planned mechanism for delivering a login OTP to a phone with no `User` row yet. **Verified against this app's actual `SmsChannel` implementation and Laravel's own `AnonymousNotifiable` source** (read directly on the server, not assumed): `SmsChannel::send()` requires the notifiable to expose either `routeNotificationForSms()` or a `->phone` property; `AnonymousNotifiable` has neither. Ad-hoc routing would have silently failed to send — not error, just silently do nothing. `OtpService` calls `SmsAdapter::send()` directly instead (same binding, same swappability, message copy still centralized in `OtpNotification::smsBody()`), avoiding the framework edge case entirely. This is the kind of thing that would have shipped as a silent bug if the login flow had only been "tested" by reading the code rather than by an actual HTTP request that checks whether an SMS was really captured — which is exactly what `AuthOtpTest` does.

## Explicit pre-production requirement (not fixed, flagged)

`LogSmsAdapter`/`LogPushAdapter` write the full message body — including, now, real OTP codes generated by the new login flow — to the Laravel application log. This was already true in spirit (any notification routed through these adapters logs its content) but **this session is the first time an OTP code flows through this pipeline at all** (the existing Service booking OTP was never delivered through any channel — see `AUTH_FORENSIC_DISCOVERY.md`'s critical finding). **A real SMS/push provider must be configured and swapped in (`AppServiceProvider::register()`'s two binding lines) before this login flow is used with real users** — otherwise every login OTP is visible in the server's log file. This is recorded here as an explicit, named pre-launch requirement, not silently accepted or worked around by inventing a separate "more secure" logging path that would just be a second notification system.

## Notification channels — current role, precisely

| Channel | Configured? | Used for |
|---|---|---|
| `mail` (Postmark/Resend/SES all present in `config/services.php`) | Yes — a real mail provider IS configured | Booking status updates, generic transactional copy (default channel) |
| `sms` | No real gateway — `LogSmsAdapter` only | Booking status SMS copy, payment status SMS copy, **login OTP (new this session)** |
| `push` (FCM/APNs) | No real gateway — `LogPushAdapter` only | Booking status push copy, payment status push copy |
| `database` (`in_app`) | Yes — Laravel's standard notifications table, real | Any notification explicitly including `'in_app'` in its resolved channel list |

## FUTURE extension points, not built this session

Push-based OTP delivery (`OtpNotification::via()` could add `PushChannel::class` once a real push provider exists and a device token is known — not useful today since login OTP is what proves a device/phone in the first place). WhatsApp/voice OTP delivery. Multi-device push (blocked on the same `devices` table gap noted in `AUTHENTICATION_ARCHITECTURE.md`).
