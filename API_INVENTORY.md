# API Inventory

Read directly from `routes/api.php` and every controller in `app/Http/Controllers/API/` — 22 lines of routing, 9 controllers, 745 lines total, all read this session. 20 endpoints total (19 Sanctum-protected + 1 unauthenticated webhook, signature-verified instead).

**Consistent patterns confirmed across every endpoint** (not just described — actually read in each controller):
- **Authorization:** profile-existence check (`$request->user()->providerProfile`/`fieldWorkerProfile`), not RBAC — role_assignments/`hasPermission()` is reserved for admin-panel screens, this is the established, deliberate convention for provider/worker/customer-facing endpoints.
- **Ownership:** every endpoint touching a specific resource re-checks it belongs to the caller server-side (`SubscriptionController::ownedOrFail()`, `WorkerJobController`'s `assigned_worker_id !== $worker->id` check, `PaymentController::createOrder()`'s `customer_id !== $request->user()->id` check) — never trusts an ID in the URL/body alone.
- **Errors:** `\RuntimeException` from an Action → `409` (business-rule conflict); validation failure → Laravel's standard `422`; not-your-resource → `403`; `findOrFail()`/`firstOrFail()` → `404`. No stack traces in any response body (all controllers catch and re-message before responding).
- **Financial idempotency:** the Razorpay webhook explicitly checks `if ($payment->status === 'captured') return;` before crediting anything — a retried webhook is a safe no-op.

## Summary

**TOTAL: 24 routes** (counting the webhook and the closure-based `/user`). **19 require `auth:sanctum`, 1 is signature-verified instead, 4 GET-only read endpoints have no meaningful side effects to test beyond auth.**

**Genuinely tested (at the Action/Service layer, verified this session):** the business logic behind #2, #3, #17, #18, #21, #22, #23, #24 — 8 of 24 have real automated coverage of *what they do*, just not of the HTTP layer itself (status codes, JSON shape, route-level auth middleware).

**Zero HTTP-level tests exist for any of the 24 routes as of this commit** — this is the most honest, important line in this document. Every claim of "tested" elsewhere in this inventory refers to the underlying Action/Service, confirmed real by reading the controller and matching it against the existing test suite, not by an HTTP request that was actually sent to the route.

**Two real findings from this read** (not fixed — flagged, since fixing would be a business-logic-adjacent judgment call, not a pure technical one):
1. `POST /api/bookings/{booking}/pay/create-order` has no check for an existing `pending` payment on the same booking before creating another — a double-tap or retry could create two local `payments` rows and two Razorpay orders for one booking. Low real-world impact (the customer would just see two checkout screens, only one can actually be paid against a captured webhook), but worth a guard.
2. `POST /api/plans/{plan}/subscribe` has no check for an existing active/pending subscription to the same plan before creating another — same shape of gap, lower severity (a genuine intentional resubscribe is a normal use case, unlike a double payment order).

Neither is a security hole (no IDOR, no auth bypass, no financial double-credit — the actual crediting is protected by the webhook's idempotency guard) — both are duplicate-*record* risks, not duplicate-*money* risks. Recorded here rather than silently fixed, since "should a second pending order silently replace the first, be blocked, or just be allowed" is a real product decision.
