## 1. Referral reward values

- **Issue:** `ReferralService::qualifyFromCompletedBooking()` reads `referral.reward_type`/`referral.reward_amount`/`referral.reward_points` via `Setting::get()` with hardcoded fallback defaults (`wallet` / `50` / `100`) baked in by a prior session.
- **Current behavior:** Every qualifying referral pays ₹50 (or 100 points) unless an admin overrides the `Setting` at some scope.
- **Risk:** Low direct risk (configurable, admin-overridable), but the *default* values were never a deliberate business decision — they were placeholder numbers from initial scaffolding.
- **Why unresolved:** Final commercial reward values are a business/marketing decision, not an engineering one.
- **Business decision required:** What should the real referral reward amount/points be, per country/franchise if it varies?
- **Safe current default:** Existing `Setting`-driven values stand; configurable, not hardcoded in code.
- **Affected modules:** Referral engine, Loyalty, Wallet.
- **Blocked:** No — engineering architecture is complete and correct; only the *number* is pending.
- **Phase 13 evidence (Glover/6amMart/1CallFix-1.8.10 parity audit — see `GLOVER_6AMMART_PARITY_AUDIT.md`):** a real prior 1CallFix production database (`DB_1cal_app_1.8.10.sql`) shows the actual value once shipped was **₹10 flat**, awarded on registration (not first completed booking), with the referral system enabled — but the `referrals` table in that dump has zero rows, meaning it was configured and never actually paid out. 6amMart's own shipped default is `0`/off. Presented as evidence only; the code default remains unchanged.

## 2. Cross-actor referral scope

- **Issue:** `ReferralService`/`Referral` model only support Customer↔Customer (`referrer_id`/`referred_id` both plain `users`, qualification = referred user's first completed booking *as a customer*).
- **Current behavior:** Partner↔Customer, Partner↔Worker, Worker↔Customer referral combinations have no qualification logic at all.
- **Risk:** None yet (feature simply doesn't exist for those combinations) — but building it requires deciding which actor-pair combinations are actually in scope for v1, and what "qualifying transaction" means for a non-customer referred party (e.g., a referred Provider's first *accepted job*, not booking).
- **Why unresolved:** Not yet built (Phase 3 of the current mission) — qualification semantics per actor pair are a product decision, not purely engineering.
- **Business decision required:** Which actor-pair combinations ship in v1; what counts as a "qualifying transaction" for a referred Partner/Worker.
- **Safe current default:** None invented; Customer↔Customer remains the only live path until this is decided.
- **Affected modules:** Referral engine.
- **Blocked:** Partially — the existing baseline (30 days active + 2–3 qualifying transactions) is documented and reusable; the per-actor-pair "what counts as qualifying" definition is not.

## 3. Anti-fraud signals for referrals

- **Issue:** No device/payment/address linkage detection, no velocity-anomaly detection, no duplicate-account detection exists anywhere in `ReferralService`.
- **Current behavior:** Self-referral is blocked, one referral per referred user is DB-unique-enforced, and (as of the full-day mission session, Phase 3) an admin can now **manually** flag any referral as fraud — `ReferralService::flagAsFraud()`, `Loyalty\Index`'s Referrals tab — which claws back the wallet credit via `WalletService::debit()` if it was already rewarded (gracefully recording, not crashing on, an already-spent balance). This is a manual REVIEW mechanism, not automatic DETECTION.
- **Risk:** Still real — nothing flags a suspicious referral proactively; an admin has to already suspect one to act on it.
- **Why unresolved:** Real fraud-signal thresholds (what device-linkage pattern counts as suspicious, what velocity is "anomalous") are themselves judgment calls that need product/risk-team input, not invented by an engineering pass.
- **Business decision required:** Which automatic fraud signals to check, and at what threshold; whether a flagged referral should ever auto-block vs. always require manual review (manual review is what exists today).
- **Safe current default:** Manual flagging only, no automatic detection, no invented thresholds.
- **Affected modules:** Referral engine, Wallet.
- **Blocked:** Partially — manual review tooling is done; automatic detection is blocked on the threshold decision above.
- **Safe current default:** None — this is a real gap, not a policy choice with a safe default.
- **Affected modules:** Referral engine, Wallet (reward payout).
- **Blocked:** Yes, for anything beyond basic architecture (a review-queue *mechanism* is buildable without inventing the actual fraud rules).

## 8. Real SMS / push provider — technical preparation done (2026-08-16, BD-8); vendor decision + real credentials still OPEN

- **Risk:** Unchanged — still High if shipped to real users without a driver + real credentials configured; login/booking OTP would still be undeliverable in that state.
- **Why unresolved:** Vendor selection + real account credentials remain a business/procurement decision this pass could not and did not make (see Provider Responsibility Map below) — the technical preparation is what a BD-8 mission this session completed; the decision itself is still open.
- **Business decision required:** Which SMS vendor — **MSG91 or GatewayAPI** (both adapters are now equally ready; this register does not recommend one over the other) — plus real account credentials for that vendor, and a real Firebase project + service-account credentials for FCM push.
- **Safe current default:** `LogSmsAdapter`/`LogPushAdapter` remain the default binding; explicitly documented as dev/QA-only everywhere they're referenced (Operations Health screen's provider-status panel — `app/Livewire/Operations/Health.php` — already flags `LogSmsAdapter`/`LogPushAdapter` as not-ok and will automatically flag `ok: true` with the real class name the moment a real driver is configured, no change needed there).
- **Affected modules:** OTP (login + booking), all transactional/marketing notifications.
- **Blocked:** Partially — the adapter/config architecture is done (this pass); actually binding a real vendor is blocked only on the business decision + procurement above.
- **Resolution — technical preparation only (2026-08-16, commit `1348057`):**
  - **Provider Responsibility Map, established by directly reading the Glover 1.8.5 reference source (not assumed from the prior audit's summary):** Glover's `otpGateway` setting selects between two STRUCTURALLY DIFFERENT mechanisms, never both at once — Firebase Phone Authentication (client-side SDK does its own SMS delivery via Google's infrastructure, server verifies the resulting ID token via Firebase Admin SDK) OR Glover's own server-generated/server-verified `OTPController`/`OTPService`, itself backed by a further-selectable SMS gateway (twilio/msg91/gatewayapi/termii/africastalking/hubtel/arkesel). **The real 1CallFix 1.8.10 dump had `settings.otpGateway='firebase'`** — meaning Firebase Phone Auth was the mechanism ACTUALLY SELECTED for OTP delivery in the one real prior deployment, not MSG91/GatewayAPI. The `sms_gateways` table's MSG91/GatewayAPI `is_active=1` rows (cited in the prior Phase 13 audit as "both active") reflect Glover's admin SMS-gateway *registry* (configured/available options, editable via a settings screen) — not which one `otpGateway` was actually set to. This is a genuine, evidence-based refinement of the prior Phase 13 framing below, not a contradiction of the underlying facts (Firebase, MSG91, and GatewayAPI were all real, configured relationships — only which one actually delivered OTP SMS is now known precisely).
    - **FIREBASE AUTH (Phone Authentication)** → NOT reused. Structurally incompatible with 1CallFix's current architecture: Firebase Phone Auth is a client-driven flow that replaces server-side OTP generation/verification, and this app's `OtpService` (hashed storage, expiry, attempt-limit+lockout, resend-cooldown, full audit trail — see `OTP_ARCHITECTURE.md`) is already a complete, tested, superior server-side engine the mission brief explicitly forbids replacing without a proven defect. None was found. Also structurally moot: Firebase has no generic "send this exact SMS text" product — Phone Auth cannot deliver an arbitrary pre-composed message (e.g. `OtpNotification::smsBody()`'s copy), only its own fixed verification flow.
    - **FIREBASE FCM** → Reused. Push-only, purely additive to the existing `PushAdapter` contract, no conflict with the OTP engine. `FirebaseFcmPushAdapter` now exists (FCM v1 HTTP API via a hand-rolled Google service-account JWT-bearer OAuth2 flow — `openssl_sign`, no new composer dependency).
    - **MSG91** → Candidate SMS provider. `Msg91SmsAdapter` now exists (MSG91's documented plain-text `SendHTTP` API, not the newer Flow/template API — this app already composes full message text server-side, and Flow requires a pre-registered template id this repo doesn't have). **Real regulatory constraint found and documented, not worked around:** Indian DLT/TRAI regulations require SMS routes/sender-ids to be pre-registered with the telecom regulator before transactional/OTP SMS can legally be sent to Indian numbers on most routes — a real production prerequisite outside this codebase's control.
    - **GATEWAYAPI** → Candidate SMS provider, equally ready. `GatewayApiSmsAdapter` now exists, its request shape mirroring Glover's own real, working implementation closely (higher structural confidence than MSG91 specifically because it's copied from a proven-working prior implementation, not built from documentation alone).
    - **INTERNAL 1CALLFIX OTP ENGINE** (`OtpService`/`Otp` model) → Unchanged, untouched, already production-ready architecture — confirmed by this pass, not just carried forward. Only the delivery adapter was ever missing.
  - Neither MSG91 nor GatewayAPI was auto-selected, per the mission's explicit instruction — both adapters were built symmetrically; whichever an operator sets `SMS_DRIVER` to is a config change, not a code change.
  - **`InvalidPushTokenException`** + `PushChannel` now clears a `User`'s stale `fcm_token` when the PUSH PROVIDER itself (not just a generic send failure) confirms the token `UNREGISTERED`/`NOT_FOUND` — "token invalidation on Firebase/FCM errors," one of this item's own original discovery questions. `LogPushAdapter` never throws it, so this has zero effect until a real push adapter is bound.
  - **NOT LIVE-VERIFIED, still explicitly required before production use:** no real MSG91 account, no real GatewayAPI account, and no real Firebase service-account credentials exist anywhere in this repository or environment. 31 new tests (all against `Http::fake()`, zero live provider calls, per the mission's own testing requirement) prove the adapters' request shape, error handling, and safety properties (no OTP code ever appears in a log line, missing credentials fail closed without an accidental request) — they do not and cannot prove a real vendor will accept and deliver a real message. A real integration test against a real sandbox/account, and a real OTP confirmed delivered to a real phone in a controlled test, remain required before this item can be marked resolved.
  - Full suite: 747/747 → 778/778, 1759 → 1799 assertions, zero regressions.
- **Phase 13 evidence (original framing, preserved — refined by the Provider Responsibility Map above, not overwritten):** the real 1CallFix 1.8.10 database shows the vendor decision was **already made in a real prior deployment**: OTP via **Firebase** (real project id `onecallfix-6b538`), SMS gateway registry included **MSG91** + **GatewayAPI** (both `is_active=1` in the real `sms_gateways` table — now understood as "configured options," not necessarily "the live-selected OTP channel," per the refinement above), push via **FCM**. 1CallFix already had a real Firebase project and an MSG91 relationship. The embedded server auth token is expired, so current credentials still need procuring — the *vendor relationship* precedent (a real Firebase project, a real MSG91 relationship) is real, unlike almost every other item in this register, but it does not by itself pick MSG91 over GatewayAPI for SMS.

## 10. Commission clawback on refund

- **Issue:** `CancellationService::refundIfPaid()` refunds the customer (via gateway or wallet credit) but never touches the `commissions` table — a booking that was already `completed` (commission applied) and is later cancelled/refunded would leave the provider's commission earnings untouched.
- **Current behavior:** No commission reversal on refund, ever.
- **Risk:** Real, but the actual boundary matters: `AdminCancelBookingAction::execute()` explicitly refuses to cancel an already-`completed` booking (`throw new \RuntimeException` for `completed`/`cancelled` statuses) — so in practice, a refund can only happen on a PRE-completion cancellation, where commission was never applied in the first place (commission only applies via `CompleteBookingAction`). **This means the clawback scenario may not be currently reachable at all** — confirmed by reading both actions directly, not assumed. Flagged here because it's the kind of gap that becomes reachable the moment a new cancellation/dispute path is added (e.g., a post-completion dispute-driven refund), not because it's exploitable today.
- **Why unresolved:** If/when a post-completion refund path is ever built, whether to claw back commission (and from whom — provider, franchise, platform, or split) is a business policy decision.
- **Business decision required:** Commission clawback policy for any future post-completion refund/dispute path.
- **Safe current default:** No post-completion refund path exists, so no clawback is needed yet. Documented here so it isn't silently invented if that path is ever built.
- **Affected modules:** Commission, Payment, Wallet.
- **Blocked:** N/A today (unreachable path); blocks only a *future* feature.
- **Update (full-day mission Phase 3):** The identical unreachable-path finding applies to referral reward clawback-on-booking-cancellation — a referral only qualifies off a `completed` booking (`ReferralService::qualifyFromCompletedBooking()`), and a `completed` booking can't be cancelled (same `AdminCancelBookingAction` guard). Referral clawback WAS built this session, but only as an admin-driven manual fraud-flag action (`ReferralService::flagAsFraud()`, reachable anytime, not gated on a booking-cancellation path) — not as an automatic reaction to a cancellation that can't currently happen. If a post-completion refund/dispute path is ever built, both this item's commission question AND a parallel "does a legitimate (non-fraud) refund also reverse the referral reward it indirectly funded" question should be resolved together.

- **Issue (historical):** `config('app.timezone')` is `UTC` (correct for storage). `countries.default_timezone` exists (e.g. `Asia/Kolkata`) and IS correctly used by `DocumentService` to compute the right local calendar date/year for invoice numbering and display. Nothing else in the codebase converted a timestamp to a viewer's local timezone before display — a repo-wide search for `setTimezone(`/`->tz(` in `resources/views` and `app/Livewire` found zero matches outside `DocumentService`. Every `->format(...)` call on a Carbon timestamp anywhere else (Bookings list/detail, Payouts, Commissions, Wallet Ledger, Operations Health, etc.) rendered in UTC.
- **Risk (historical):** Medium — not a security issue, but a real, present correctness/usability gap: an admin scheduling or reviewing a booking around a time boundary (e.g. late evening IST, which crosses UTC's midnight) could misread which calendar day a booking falls on. Real production data is confirmed India-based (`GLOVER_6AMMART_PARITY_AUDIT.md`), so this was a present-day issue, not a future-country hypothetical.
- **Resolution (2026-08-16, Phase 21 item TECH-3, commit `ba4f72e`):** New `app/Services/TimezoneResolver.php` converts each row's own `franchise → country → default_timezone` before display, falling back to `config('app.timezone')` when no franchise/country applies — the design choice this item itself named as still-open (a helper reading the row's own franchise chain) was the one adopted, not the simpler single-tenant `config('app.display_timezone')` alternative. Applied across the franchise-scoped operational screens: Banners, Bookings, Commissions, Customers, Flash Sales, KYC Support Requests, Loyalty, Payments, Providers, Subscriptions, Wallet Ledger, Workers, and Operations/Health's dispatch- and stuck-booking timestamps specifically. 23 new regression tests in `TimezoneDisplayTest.php`, including a UTC-midnight boundary case (a timestamp that renders on a different calendar day once converted), a stored-value-not-mutated assertion, and 2 N+1 guards.
- **Deliberately still UTC (not an oversight — franchise-agnostic system/audit data):** `failed_jobs`, `scheduled_task_runs`, `payment_webhook_logs`, `NotificationLog.sent_at`.
- **Deferred, not decided (found during this pass, left untouched — no timezone policy invented for them):** `PerformanceCampaign.starts_at`/`ends_at`, `FlashSale.starts_at`/`ends_at`, `BadgeAssignment.expires_at`, `NotificationMeeting.starts_at`. Whether these should convert to franchise-local time, stay UTC, or use some other policy (e.g. a campaign that starts/ends by one shared wall-clock time regardless of franchise) was not decided or assumed.
- **Business decision required:** None for the resolved screens — that was a pure engineering correctness fix, as originally assessed. The four deferred timestamps above remain a genuinely open question (policy, not yet a decision to make).
- **Affected modules:** Franchise-scoped operational admin screens (resolved); the four deferred models above (still open).
- **Blocked:** No, for the resolved screens — closed. Yes, for the four deferred timestamps — blocked on the same kind of design decision this item itself was blocked on, not yet made.

## 28. `CampaignService::send()`/`resendToFailedRecipients()` load the entire resolved audience into memory in one `->get()` rather than chunking — RESOLVED (2026-08-16)

- **Issue (historical):** Both methods ran `$recipients = $this->audienceResolver->resolve(...)->get();` (or `User::whereIn('id', $failedUserIds)->get()`) then looped, hydrating every matching recipient as an Eloquent model in a single PHP array before sending a single notification. `KycReminderService::dispatchDue()` — the one other real bulk-notify loop this same audit phase found — already used `chunkById(200, ...)` for exactly this reason; `CampaignService` never adopted that pattern.
- **Risk (historical):** Low-to-medium and shrinking as the user base grows: at 1CallFix's current scale this was a non-issue (a few thousand rows costs low-single-digit MB); it only becomes a real memory-limit risk at an audience size well beyond today's single-country footprint. Never a correctness bug — the recipient list itself was always 100% accurate either way.
- **Resolution (2026-08-16, Phase 21 item TECH-7, commit `df4e186`):** Both methods rewritten to `chunkById(200, ...)`, matching `KycReminderService::dispatchDue()`'s own established pattern exactly — an accumulated counter replaces `$recipients->count()`, no behavior change to callers. 3 new regression tests, including a query-count assertion proving 205 recipients (crossing the chunk boundary) produce exactly 2 SELECTs against `users`, not 1 (the old behavior). Verified via `git stash` that the query-count test genuinely fails without the fix.
- **Business decision required:** None — was a pure engineering follow-up, as originally assessed.
- **Affected modules:** `App\Services\CampaignService::send()` and `::resendToFailedRecipients()`.
- **Blocked:** No. Closed.

## 29. `FlashSaleService::priceFor()`/`::redeem()` are never called from the real booking-creation path — Flash Sale discounts have no effect on any actual booking today

- **Issue:** Discovered 2026-08-16 during Phase 21 item BD-12's own "verify in code whether an actual stacking guard exists" check (a read-only verification, not a decision). A repo-wide search for real callers of `FlashSaleService::priceFor()` and `::redeem()` found **none** outside the class's own file and `FlashSaleEngineTest`. `App\Livewire\FlashSales\Manage` (the admin screen) only calls `remainingQuantity()` for display — never `priceFor()`/`redeem()`. `app/Actions/CreateBookingAction::execute()` — the single real entry point for every booking, "from the customer app or a Tinker test alike" per its own docblock — computes `price_quoted` from `$service->base_price` (or an explicitly supplied override) adjusted only by `EntitlementService::resolveAndConsumeForBooking()` (the Plan Engine's own entitlement discount). No Flash Sale call exists anywhere in that path. No API controller under `app/Http/Controllers/API/` references `FlashSale` at all, so a Flash Sale's discounted price is never even advertised to a customer, let alone charged.
- **Current behavior:** An admin can create, schedule, target, and activate a Flash Sale through a fully working, permission-gated, tested admin screen — `FlashSale`/`FlashSaleTarget`/`FlashSaleRedemption` are all real schema, `FlashSaleService::priceFor()`/`::redeem()` are both real, correct, unit-tested methods (per `FlashSaleEngineTest`) — but none of it currently changes what any real customer sees or pays. The engine is real and internally correct; it is simply not wired to the booking pipeline it was built to discount.
- **Risk:** Not a security or financial-integrity issue (nothing is mis-charged, since the discount never applies either way — the customer always pays the normal price). Real functional-completeness/trust gap: an admin who runs this screen today reasonably expects it to affect real bookings, and it silently does not. Matches the same "orphaned mechanism" shape this mission has repeatedly found and fixed elsewhere (Tips before Phase 11, Reviews before Phase 13, in-app notifications before Phase 8) — except in each of those prior cases the missing piece was a thin API/controller layer over an otherwise-complete service; here, wiring a Flash Sale into `CreateBookingAction` also requires resolving item 12's own still-open stacking question (Flash Sale vs. Plan discount, both potentially applicable to the same booking) before the wiring can be written correctly, not just mechanically.
- **Why not fixed in this pass:** Wiring `FlashSaleService` into `CreateBookingAction` is a real, non-trivial feature-completion task (discount application at booking-creation time, real-time redemption/quantity-decrement concurrency handling, and — as this finding itself shows — a prerequisite dependency on item 12's stacking decision) — not a minimum, logically-inseparable part of BD-12's own narrow "verify a stacking guard exists" ask. Building it unilaterally here would be exactly the kind of unrelated, speculative feature work this pass's own operating rules forbid bundling into another item.
- **Business decision required:** Item 12's stacking question (Flash Sale × Plan, since Coupons remain dormant per item 7) must be answered before this can be wired correctly — otherwise the wiring itself would silently make an unreviewed stacking-policy choice by construction. Also worth a product decision on urgency: is a live, booking-affecting Flash Sale mechanism wanted for this release, or does the admin screen stay a configuration-only preview until then?
- **Safe current default:** Unchanged — Flash Sale configuration has zero effect on real bookings today, which is a safe (if functionally incomplete) state; no customer is overcharged, undercharged, or shown a price they won't actually get.
- **Affected modules:** `App\Services\FlashSaleService::priceFor()`/`::redeem()`, `App\Actions\CreateBookingAction`, item 12 (stacking).
- **Blocked:** Yes — on item 12's stacking decision, plus a product call on whether/when to prioritize the wiring itself.
