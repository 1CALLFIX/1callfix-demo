13. **Financial reconciliation audit (mission Phase 15).** Audited every money-moving path this mission has built — campaigns, compensation, tips, referrals, payouts, loyalty, wallet top-ups — for real financial-integrity gaps rather than guessing at candidates. Found and fixed one genuine race: `LoyaltyService::redeem()` checked its unlocked `SUM()` balance *before* opening its transaction — two concurrent redemptions for the same user could both read a sufficient balance and both succeed, driving the aggregate ledger negative. Fixed by moving the check inside the transaction, behind a `lockForUpdate()` on the user's own ledger rows — the exact same guarantee `WalletService` already gives `wallets.balance`, just applied to the ledger-only loyalty balance for the first time. Extended `ReconciliationService` (Phase 10) with two new read-only detection checks, both surfaced on the existing Operations/Troubleshoot screen: wallet top-ups Razorpay captured but never credited (`RazorpayWebhookHandler`'s Payment-capture and wallet-credit are two separate, non-atomic transactions — a process death between them leaves real captured money with no matching `WalletTransaction` ever landing) and negative aggregate loyalty balances (the detection half of the race above, catching anything that slipped through before the fix or via a future bypass). Campaigns/Compensation/Tips/Referrals/Payouts were all confirmed — by reading their actual code, not assumption — to already route every credit through `WalletService`/`CommissionService` with real DB-level idempotency guards (unique constraints or existence checks) and needed no new check. 14. **API/security/E2E hardening sweep (mission Phase 16).** Read every API controller under `app/Http/Controllers/API/` against its actual route in `routes/api.php` (17 controllers, 40+ endpoints) for real IDOR/authorization gaps rather than guessing at candidates. Found the API layer itself already well-guarded — every controller re-checks ownership server-side (booking participancy, payment-account `user_id`, subscription `subscribable`, worker `assigned_worker_id`), documented in its own docblock, none trusting a route-param id alone. The two real gaps found were structural, not per-endpoint: (1) **zero general-purpose API rate limiting existed anywhere** — `bootstrap/app.php` never called `throttleApi()`, and no `RateLimiter::for('api', ...)` was registered; only the 6 explicit auth/OTP/QR routes had their own throttle, meaning every other authenticated route (wallet top-up, loyalty redeem, payment order creation, chat, subscriptions) could be called at unlimited volume by any valid Sanctum token. Fixed with Laravel's own standard starter-kit default (60/min, keyed per authenticated user or per IP for guests) via a new `RateLimiter::for('api', ...)` in `AppServiceProvider::boot()` + `$middleware->throttleApi()` in `bootstrap/app.php` — an honest engineering default, not an invented business number. (2) **9 of the pre-existing 24 business-logic API routes (WalletController::show, LoyaltyController, ProviderDiscoveryController, PlanController, SubscriptionController's 7 endpoints, PartnerWorkerController) had zero HTTP-level test coverage** — the implementation was correct on inspection but unproven at the layer a real mobile client actually calls, exactly the gap `PROJECT_CURRENT_STATE.md` §24 P4 already named. Closed with 6 new HTTP-level test files (`WalletApiTest`, `LoyaltyApiTest`, `ProviderDiscoveryApiTest`, `PlanApiTest`, `SubscriptionApiTest`, `PartnerWorkerApiTest`), each proving auth-required, IDOR rejection (one user's request can never read/mutate another's wallet/points/subscription), and the happy path — plus `ApiRateLimitTest` proving the new limiter is actually wired onto a real, previously-unthrottled route (429 past 60 req/min, scoped per-user not globally). Investigated and deliberately NOT built: Sanctum token expiration/revoke-list (a genuine mobile-session-lifetime product decision entangled with a real but bounded feature gap — logged as risk register item 24) and verifying production's real `APP_DEBUG` value (requires live production access this session didn't have/use — logged as risk register item 25, the single highest-severity item in the register if that value turns out to be `true`). Browser-driven E2E (`Playwright`/Dusk-style multi-actor journeys) remains explicitly out of scope for this phase, same as every prior mention in `PROJECT_CURRENT_STATE.md` §24 P8 — not silently dropped, just not attempted here. 33 new tests. Full suite 616/616.

Razorpay's India-only scope (already documented, item 9) and multi-language/locale content (already documented, item 18) were confirmed still accurate, not re-logged.
