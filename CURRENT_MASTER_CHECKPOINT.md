12. **Master Catalog Import + Operations Import/Export completeness (mission Phase 14).** User-supplied real historical catalog spreadsheets plus real screenshots of the reference product's live `/central/operations/{imports,exports,backup}` screens. Found the existing Categories/Subcategories/Services import (built in an earlier, unlogged session) had real, working Upload→Validate→Preview→Commit UI but **zero test coverage** and reused a source file's `id` column directly as the real database primary key — exactly the practice the new spec explicitly forbids, since it means a future import could collide with or overwrite an unrelated real row. Rebuilt around a new shared engine, `App\Services\Catalog\CatalogImporter` (+ `CategoryImporter`/`SubcategoryImporter`/`ServiceImporter`): a new nullable-unique `external_id` column on all three catalog tables decouples the real PK from any source system's identity — row matching is external_id-only, and relationship columns (category_id/subcategory_id) resolve via a two-step external_id-then-real-id lookup that correctly handles both a fresh historical import and a round-trip re-export/re-import of 1CallFix's own catalog. Every commit is wrapped in one DB transaction (genuine rollback-on-partial-failure) and persists a new `catalog_import_runs` audit row (created/updated/unchanged/deactivated/skipped/failed counts + full per-row JSON detail) — a real Import Report, not an ephemeral message. Deactivate-missing is opt-in and only ever touches externally-sourced rows, never a manually-created one. `vendor_Type_id` 5/9 (confirmed real historical values) map to the existing `service`/`commerce` `App\Support\Modules` slugs; an unrecognized value is a validation error, never a guessed default. Investigated Vendors/Menus/Products import (the reference product's own Data Import screen has them) and a database-backup screen (the reference product's own Data Backup screen) — both deliberately NOT built (no target schema for the former; a "download the full production DB" feature is a real exfiltration risk to improvise without knowing the real deployment environment for the latter) — logged as new risk-register items (20, 21) instead. Added real Earnings/Payouts exports (`CommissionsExport`/`PayoutsExport`, matching the reference product's own Data Export screen) reusing existing ledger data as source of truth, never recalculated, with sensitive banking fields (account_number/ifsc) masked to last-4 only — found and logged (not silently fixed) that `Payouts\Manage` itself has no row-level franchise scoping, unlike `Commissions\Index` (risk register item 22). 39 new tests across `tests/Feature/Catalog/*` (importer engine, relationship resolution, idempotent re-import, rollback-on-partial-failure, authorization/global-scope-restriction, real end-to-end CSV upload) and `tests/Feature/Operations/DataExportTest.php` (row-level export scope, sensitive-field exclusion, financial-value correctness).
